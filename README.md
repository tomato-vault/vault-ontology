# vault-ontology

[![English](https://img.shields.io/badge/lang-English-blue)](README.en.md)

> Obsidian vault의 문서 4,400+개를 **기계가 읽을 수 있는 그래프**로 만들면서 온톨로지를 손으로 배운다.
> 같은 데이터를 **두 번 모델링한다** — 속성 그래프로 한 번, RDF 온톨로지로 한 번.

## 하이라이트

- **같은 vault를 두 번 모델링한다** — 1부(Phase 1~5)는 SQLite 속성 그래프, 2부(Phase 6~9)는 RDF · SPARQL · RDFS/OWL · 추론. 같은 질문("A를 이해하려면 뭘 먼저 읽어야 하나")을 재귀 CTE로 한 번, property path로 한 번, 추론기로 한 번 푼다. **답은 같아야 하고, 표현력은 달라야 한다.** 그 차이가 「지식 그래프」와 「온톨로지」의 핵심이다
- **답안지를 옆에 두고 백지에서 다시 짠다** — 이미 동작하는 `vault-cli`(1,142줄)를 `reference/`에 커밋 스냅샷으로 고정해 두었다. **막히기 전에는 열지 않는다.** Phase 1~5까지만 답이 있고, 2부에는 답안지가 없다
- **답안지와 갈린 다섯 지점에서 모두 이 구현이 맞았다** — 동명이인 해석(링크 126) · 정본엔 있는데 구현엔 없던 검사(23) · 이미지 임베드 오인(582) · `part_of` 전역 이름 조회(139) · 태그 집계(3,319)
- **코드보다 vault가 먼저 개선됐다** — 스키마 정본 v1.8(`builds_on` 선택 기준 신설) · CLAUDE.md v2.43 · 죽은 태그 어휘 13종 삭제 · **끊겨 있던 pre-commit 훅 복구**(홈 디렉터리 이름이 바뀌면서 경로가 깨져, 커밋은 모두 막으면서 유실 검사는 하나도 못 하던 상태였다)
- **테스트 241개, Phase 1~5는 외부 의존성 0** — 파서를 손으로 짜는 것이 목적이라 표준 라이브러리만 썼다. `rdflib`과 `owlrl`은 온톨로지를 다루는 2부에서만 사용한다
- **실측이 판정한다** — 단위 테스트가 전부 초록이어도 실제 vault에서 숫자가 다르면 틀린 것이다. 1부 내내 「조용히 틀리는 실패」가 다섯 번 나왔고, 의심하는 법을 [`learnings/silent-failures.md`](learnings/silent-failures.md)에 따로 정리했다

> **현재 상태**: Phase 1~9 완료 (2026-08-25), Phase 10~19 계획 수립. 2부의 결론인
> **SQLite 상시 운용·RDF/OWL 학습/상호운용**은 유지한다. 3부는 검색 개선이 아니라
> 문서 안의 주장·사건·결정·원칙과 근거를 다루는 별도 의미 온톨로지 작업이다.
> 대상은 개발 지식에 한정하지 않고 개인 경험·성찰·철학·커리어·생활을 포함한 Vault
> 전체이며, 각 영역의 맥락을 보존하면서 서로 영향을 주는 접점을 찾는다.

## 왜 만들었나

온톨로지라는 말은 대략 알고 있었다. 최근 동료 개발자들과 이야기하면서 조금 더 자세히 알게 됐고, 듣는 동안 계속 내 Obsidian vault가 떠올랐다.

vault의 취지 자체가 **개발하면서 얻은 지식의 데이터베이스**였다. 문서 4,400+개가 위키링크 11,624개로 이미 얽혀 있다. 사람 눈에는 분명 그래프인데, **기계가 읽을 수 있는 구조가 없다.** 처음에는 온톨로지가 정확히 그 자리에 들어맞는 도구라고 생각했다. 이 프로젝트는 그 가설을 실제 vault로 검증한 기록이다.

그래서 두 가지를 동시에 한다.

1. **온톨로지를 제대로 배운다** — 이게 첫째다. 읽어서 아는 것과 직접 짜서 아는 것이 다르다는 걸 확인하러 왔다
2. **내 vault에 실제로 도입한다** — 학습용 장난감 데이터가 아니라 매일 쓰는 vault를 쓴다. 안 맞으면 안 맞는다고 결론내는 것도 산출물이다

여기에 한 가지 이유가 더 있었다. vault를 SQLite로 뽑아내는 `vault-cli`는 **이미 동작한다. 다만 내가 짜지 않았다.** Claude가 만들었고, 돌아가지만 내 의도와 어긋난 자리가 남아 있다. 그래서 파서부터 그래프 빌더까지 백지에서 다시 짜고, 기존 코드는 **권위가 아니라 검토 대상**으로 옆에 둔다. "정본에 그렇게 적혀 있다"는 논증의 끝이 아니라 시작이다.

실제로 1부에서 그 간극이 **코드의 우위와 vault의 개선** 양쪽으로 나타났다.

## 이 프로젝트에서 말하는 온톨로지

「온톨로지」는 문맥에 따라 서로 다른 세 가지를 가리킨다. 이 프로젝트가 무엇을 만들고 무엇을 원했는지 구분하려면 먼저 이 좌표를 잡아야 한다.

| 갈래 | 묻는 것 | 이 프로젝트에서 |
|---|---|---|
| **① 철학의 존재론** | 이 세계에 무엇이 존재한다고 볼 것인가 | vault에 문서·폴더·태그·13가지 `type`이 있으며, 폴더와 파일은 다른 존재라고 정했다 |
| **② Gruber·지식공학의 온톨로지** | 공유된 개념화를 명시적이고 형식적으로 어떻게 적을 것인가 | `vault-ontology.ttl`에 RDFS/OWL 공리를 적고 추론기를 돌렸다 |
| **③ 업계의 운영 온톨로지** | 데이터에 로직·액션·권한을 붙여 실제 운영을 어떻게 움직일 것인가 | AI 에이전트가 vault를 탐색하고 다음 행동을 고르게 하려던 원래 목적이 이쪽에 가깝다 |

**만든 것은 ②지만, 풀고 싶었던 문제는 ③에 가까웠다.** 이 프로젝트는 Markdown 파일 묶음을 억지로 온톨로지로 바꾸려 한 것이 아니다. vault를 문서·관계·규칙이 함께 움직이는 **개인 지식 운영 환경**으로 보고, 그 구조를 기계가 읽게 만들 때 형식 온톨로지가 실제로 필요한지 확인했다.

결과적으로 RDFS/OWL 추론이 SQLite에서 얻을 수 없던 유용한 사실은 0건이었다. 그래서 Markdown을 원본으로 두고 SQLite 그래프를 상시 운영에 사용하며, RDF/OWL은 개념을 엄밀히 확인한 학습·상호운용 산출물로 남긴다. **②를 직접 만들어 봤기 때문에 ③의 목적에 필요한 도구가 무엇인지 구분할 수 있었다**는 것이 이 프로젝트의 결론이다. 자세한 판정 근거는 [`learnings/verdict.md`](learnings/verdict.md)에 있다.

## 사용 시나리오

매일의 목적은 하나다. **AI 에이전트로 vault를 탐색하기 쉽게 만드는 것.**

예를 들어 이렇게 묻는다.

> "지금 프로젝트에서 Redis 커넥션 풀 문제를 겪고 있어. 읽어보면 좋을 문서를 골라줘."

그러면 에이전트가 구역의 성격을 살려 답한다.

- **200 Dev Knowledge Base** — 객관적 사실·범용 지식 (커넥션 관리의 일반 원리)
- **300 Runtime** — 다른 프로젝트에서 실제로 겪은 것 (E-Project에서 같은 문제를 어떻게 풀었나)
- **400 Logic Forge** — 선택이 걸린 자리의 trade-off (풀 크기 vs 지연)

또는 "Docker를 설명하는 문서를 전부 나열해줘" 같은 단순 검색도 grep이 아니라 그래프에 묻는다 — `q tag Stack/Docker`, `q near`로 역링크·같은 태그 이웃까지.

`q path`가 대표 질의다. `builds_on`을 따라 올라가 "이걸 이해하려면 뭘 먼저 읽어야 하나"를 학습 순서로 낸다. 파일시스템 탐색이나 grep으로는 한 단계는 봐도 이행 폐쇄는 못 한다.

**이 검색 경험이 목적이고, 온톨로지·그래프는 그걸 떠받치는 수단이다.** 4,400+개 문서를 사람이 다 기억할 수 없으니, 구조화된 frontmatter가 에이전트에게 "어디에 무엇이 있는지"를 알려준다.

## 두 번 모델링한다

```
                  +-----------------------------------------------+
                  | 4,400+ Markdown notes (source vault)          |
                  |                                               |
   Phase 1-3      | Parse                                         |
   ---------      |   frontmatter / wikilinks / file index        |
                  |      v                                        |
   Phase 4        | Validate                                      |
   ---------      |   "everything built must pass validation"     |
                  |      v                                        |
                  |  +-------------------+                        |
   Phase 5        |  | SQLite graph      |  Part 1 output         |
   ---------      |  | node / edge / tag |  Part 2 baseline       |
                  |  +-------------------+                        |
                  |      v                                        |
   Phase 6-9      | RDF triples                                   |
   ---------      |   SPARQL / RDFS / OWL / SKOS / reasoning      |
                  +-----------------------------------------------+
```

**한 단계에 변수 하나씩만 바꾼다.** Phase 5까지의 산출물이 Phase 6~9의 회귀 대조본이 된다.

출발점은 스키마 설계 문서에 이미 적어둔 한 문장이었다.

> **속성 그래프(Neo4j) ≠ 온톨로지.** 형식 의미론도 추론기도 없다. 온톨로지를 배우려면 RDF 계열이 맞다.

즉 지금의 SQLite 그래프는 **지식 그래프이지 온톨로지가 아니다.** 그걸 손으로 재현해두고 2부에서 진짜 온톨로지로 넘어간다. 같은 데이터로 두 번 모델링해봐야 그 차이가 말이 아니라 경험으로 남는다.

## 진행 방식

```
RED       테스트를 쓴다 → 실패 메시지를 함께 읽는다
GREEN     최소 구현 → 통과 → 커밋
REFACTOR  개선점 검토 (없으면 "없다"고 판단하는 것도 결과) → 있으면 별도 커밋
실측       실제 vault에 돌려 답안지 출력과 대조
```

마지막 줄이 이 프로젝트의 판정 기준이다. **초록은 「구현이 테스트와 맞는다」만 말한다. 「테스트가 옳다」는 실제 데이터가 알려준다.**

파서는 TDD가 특히 잘 맞는다. 함정이 전부 "이 입력에 대해 이 출력"의 형태이기 때문이다. `vault-cli` README의 **"이 자리에서 네 번 잘못 셌다"** 표가 그대로 테스트 케이스 목록이 됐다.

| 함정 | 증상 | Phase |
|---|---|---|
| `\s*(.+)$` | `\s`가 개행을 먹어 빈 `summary:`가 다음 줄을 읽는다 | 1 |
| 표 안의 `\|` | `[[문서\|별칭]]` 타깃 끝에 역슬래시가 남는다 | 2 |
| `splitext` | `No.013 현자의 돌` → `No` + `.013 현자의 돌` | 3 |
| 유니코드 정규화 | macOS는 파일명을 NFD로 저장한다. 본문 링크는 NFC | 3 |
| 대소문자 | macOS는 `python`과 `Python`을 구분하지 않는다 | 3 |
| `2026-13-99` | 형태는 맞는데 없는 날짜다 | 4 |

문자열 접두사가 경계를 제대로 구분하지 못하는 문제는 **다섯 번** 나왔다. 정규식 조각 사전은 [`learnings/regex-reference.md`](learnings/regex-reference.md)에 있다.

책 챕터 필사 914개는 저자의 말이고, 700 Life Stack은 판단이 아니라 사전이다.

### 성공 기준

"코드가 돌아간다"는 성공 기준이 아니다. 도구를 하나 더 만드는 것으로 끝날 위험이 실재하고, 원본 프로젝트 문서도 그 위험을 스스로 적어뒀다 — **지식 정리 자체가 목적이 되어 실제 행동을 미루는 기계가 되는 것.** 그 위험을 알고 시작했다.

- [x] Phase 5 — 실측값 표를 **손으로 짠 코드로** 재현했다
- [x] Phase 8 — `type`의 13가지 값에는 의미별 묶음보다 **Content·Imported·Structural 3역할 계층**이 유용하다고 결론냈다
- [x] Phase 9 — 추론이 만든 사실을 측정했다. **SQLite로 얻을 수 없던 유용한 사실은 0건**이었다
- [x] 최종 — **재귀 CTE로 충분하다.** rdflib 상시 운용은 하지 않는다

3부는 다음을 별도로 판정한다.

- [ ] 문서와 실제 지식 개체를 분리하고 안정 ID를 유지한다.
- [ ] 기존 도구로 답하지 못한 역량 질문을 정확히 답한다.
- [ ] 모든 의미 사실과 파생 결과가 원문 근거로 돌아간다.
- [ ] 제안·추론·승인 상태가 섞이지 않고 철회 가능하다.
- [ ] 실제 사용 가치가 annotation과 검토 비용보다 크다.
- [ ] 쓰기 작업은 shadow mode·preview·승인·감사·rollback을 통과한다.
- [ ] 개발·개인·철학·커리어·생활 지식의 접점을 근거와 함께 설명한다.

마지막 항목이 진짜 산출물이다. 예상과 달리 0건이 나왔지만, 그 결과 덕분에 운영 도구와 학습 도구의 역할을 분명히 나눌 수 있었다.

## 2부 결과와 최종 판단 (2026-08-25)

### SQL과 SPARQL

Phase 5의 여섯 질의를 Phase 7에서 SPARQL로 다시 구현했다. property path는 이행 폐쇄와 역방향 순회를 표현하는 질의를 크게 줄였지만, 새로운 종류의 질의를 가능하게 하지는 않았다.

| 질의 | SQLite | rdflib | 결과 |
|---|---:|---:|---|
| `path` | 0.5ms | 2ms | SPARQL이 간결하지만 깊이 정보는 잃는다 |
| `near` | 0.0ms | 7ms | `^`로 역방향을 간결하게 표현한다 |
| `orphans` | 0.0ms | 281ms | 표현은 비슷하고 SQLite가 훨씬 빠르다 |
| `kinds` | 0.0ms | 60ms | 표현은 비슷하고 SQLite가 훨씬 빠르다 |

모든 질의에서 SQLite가 10~600배 빨랐다. 자세한 비교는 [`learnings/phase07-sparql-vs-sql.md`](learnings/phase07-sparql-vs-sql.md)에 있다.

### 어휘와 추론

`type`의 13가지 값을 억지로 의미별 계층에 넣지 않고, 실제 질의에 도움이 되는 세 역할만 남겼다.

```
Document
├── Content       내가 쓴 내용
├── Imported      외부에서 가져온 자료
└── Structural    허브와 템플릿
```

OWL RL 추론은 트리플을 27,587개에서 77,478개로 늘렸다(2.81배, 16.6초). 이행 관계 303개와 역링크 8,292개를 물질화했지만, 둘 다 SQLite가 질의 시점에 이미 계산하던 사실이었다. 새로 생긴 `rdf:type` 트리플 중 `rdfs:Resource`와 `owl:Thing` 14,656개는 실제 질의에 도움이 되지 않았다.

더 중요한 수확은 실패에서 나왔다. 너무 넓게 선언한 `domain` 하나가 폴더 764개를 `Document`로 추론했고, OWL의 열린 세계 가정에서는 "summary가 없으면 위반"이라는 검증 규칙을 표현할 수 없었다. **OWL은 추론, SHACL은 검증**이라는 경계를 실제 데이터로 확인했다.

최종 결정:

- 상시 운용은 SQLite 구현을 사용한다
- RDF 산출물은 학습과 상호운용을 위해 남긴다
- rdflib 기반 v1은 진행하지 않는다
- Oxigraph 기반 v2는 성능 때문이 아니라 추가 학습이 필요할 때만 재검토한다
- 분리된 `800 TRPG` 코퍼스는 두 저장소를 함께 물어야 하는 질의가 생길 때 합친다

전체 판단과 근거는 [`learnings/verdict.md`](learnings/verdict.md)에 정리했다.

## 실행

```bash
uv sync
uv run pytest -v          # 241개 통과해야 정상 출발점
```

vault 경로 기본값은 `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/Obsidian Vault`이고, 모든 명령이 `--vault`를 받는다.

```bash
uv run python -m vault lint          # 스키마 정본 대비 위반 (현재 382건)
uv run python -m vault build         # .vault-graph.db 재생성 — 매번 지우고 새로 만든다
uv run python -m vault rdf           # .vault.ttl 재생성

uv run python -m vault q stats
uv run python -m vault q path "CIDR"     # 이걸 이해하려면 뭘 먼저 읽어야 하나 (재귀 CTE)
uv run python -m vault q near "CIDR"     # 링크 · 역링크 · 같은 태그 이웃
uv run python -m vault q type concept
uv run python -m vault q tag Stack/Python
uv run python -m vault q orphans 200     # 아무도 안 가리키는 문서
```

종료 코드는 `0` 정상 · `1` 위반 있음 · `2` 실행 불가. **출력만 하는 도구는 CI에도 pre-commit 훅에도 넣을 수 없다.**

`q path`가 대표 질의다. `builds_on`을 여러 단계 따라 올라가 학습 순서를 낸다. **파일 시스템 탐색이나 grep만으로는 할 수 없는 일이다** — 한 단계는 볼 수 있어도 이행 폐쇄는 계산할 수 없다.

### 설계 결정 몇 가지

| 결정 | 근거 |
|---|---|
| 그래프는 **파생물**이다. 매번 지우고 새로 만든다 | md가 원본이다. MERGE도 제약조건도 멱등성도 필요 없다 |
| `edge.dst`는 NULL을 허용하고 `raw`를 같이 저장한다 | **깨진 링크도 그래프의 사실이다.** 버리면 "무엇을 가리키려 했는가"를 잃는다 |
| 파생 가능한 사실은 저장하지 않는다 | `part_of`는 빌드 시점에 경로에서 유도한다. `updated`도 안 쓴다 — git이 안다 |
| 정규화는 **경계에서 한 번만** | 링크 5,341개(21.9%)가 여기 걸려 있다 |
| 동명이인은 이름이 아니라 **해석기**로 해결한다 | 경로가 아는 걸 파일명에 또 넣지 않는다 |
| lint 제외는 코드가 아니라 **커밋되는 설정 파일**에 | 무엇을 왜 뺐는지가 감사 대상이다 |
| 기본값은 비운다 | 설정이 없으면 전부 검사한다. 안전한 방향 |

전체 목록은 [`docs/NEXT.md`](docs/NEXT.md)의 「여기까지 오면서 확정한 것」에 있다.

### `reference/`가 무엇인가

Claude가 짠 `vault-cli`(단일 파일 1,142줄)를 **커밋된 `HEAD` 그대로** 복사해둔 회귀 대조본이다. 작업 트리가 아니라 커밋을 복사한 이유는 문서와 실측 숫자가 서로 맞아야 하기 때문이다.

**막히기 전에는 열지 않는다.** TDD 사이클을 도는 동안은 테스트가 명세다. 답안지를 먼저 보면 "왜 이렇게 짜야 하는가"를 건너뛰고 "어떻게 짰는가"만 남는다.

여는 시점은 셋이다 — 30분 이상 막혔을 때 · **Phase 5 대조(필수)** · Phase가 끝난 뒤 비교. 자세한 규칙은 [`reference/README.md`](reference/README.md).

**Phase 6~9에는 답안지가 없다.** 그쪽 대조본은 Phase 5에서 직접 만든 SQLite 그래프다.
