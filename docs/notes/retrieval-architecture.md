## 한 줄 답

**온톨로지를 더 쌓지 말고, 로컬 임베딩 벡터 검색 한 겹을 더한다.** 기존 SQLite
그래프는 증거 저장소가 아니라 **라우팅·이웃 확장** 도구로 역할을 고정한다.

## 외부 근거 (검증 통과분)

### 1. 그래프 대 벡터는 승자가 없다. 질의 유형이 가른다 — 확신 높음

통제된 평가(256토큰 청크·공유 임베딩·동일 생성기)에서 단일 홉 QA는 순수 RAG가
이기고(NQ F1 64.78 vs GraphRAG 63.01 vs KG-only 34.28), 다중 홉은 그래프가
이긴다(HotpotQA 63.01 vs 60.04). 원문: *"RAG and GraphRAG exhibit complementary
behaviors rather than a consistent winner."*

**내 두 사례는 둘 다 벡터 구간이다.** "Docker 문서 전부 나열"과 "이 상황과 비슷한
문서 추천"은 단일 홉·의미유사 계열이다. — [arXiv 2502.11371](https://arxiv.org/abs/2502.11371) (KDD 2026), [2604.09666](https://arxiv.org/abs/2604.09666)

### 2. 벤치마크의 "GraphRAG 패배"를 내 상황에 옮기면 안 된다 — 확신 높음

GraphRAG가 QA에서 지는 **원인은 그래프 개념이 아니라 LLM이 자동 추출한 KG의
정보 손실**이다. 정답 엔티티의 65.8%(HotpotQA)·65.5%(NQ)만 구축된 KG에 존재했다.

내 그래프는 **사람이 직접 유지한** 위키링크 11,624개와 통제 어휘 257종이다. 이
실패 모드가 구조적으로 면제된다. 게다가 HippoRAG 2가 이 손실을 우회한 설계
(원문을 증거로 두고 KG는 라우팅·재순위에만 사용)가 **내 현행 구조와 같은 모양**
이다. — [arXiv 2502.11371](https://arxiv.org/abs/2502.11371), [2502.14802](https://arxiv.org/abs/2502.14802)

### 3. 이 규모에서는 파이프라인을 늘리는 쪽이 과잉설계다 — 확신 높음

45,491청크 코퍼스 실측: 다중질의 확장이 재현율을 못 올리고(0.839 vs 밀집 0.887)
**정밀도를 13.8pp 깎았으며** LLM 호출을 3배로 늘렸다. 저자들은 원인을 코퍼스
규모로 돌린다 — 질의가 어느 정도 구체적이면 확장이 해소할 모호성이 애초에 없다.

**내 vault는 1~2만 청크로 더 작다. 논거가 더 강하게 적용된다.** — [arXiv 2605.02520](https://arxiv.org/pdf/2605.02520), [2604.01733](https://arxiv.org/html/2604.01733v1)

### 4. 그래프+벡터 하이브리드의 이득은 작다 — 확신 중간

최고 단일 방식 대비 Selection +1.1%, Integration +6.4%. Integration은 **모든
질의마다 검색기를 둘 다 돌린다.** 요약형 질의에서는 순수 RAG 대비 신뢰할 만한
이득이 없었다. — [arXiv 2502.11371](https://arxiv.org/abs/2502.11371), [2507.03608](https://arxiv.org/abs/2507.03608)

### 5. 완전 로컬 경로가 실재한다 — 확신 높음

`nlpai-lab/KURE-v1` (bge-m3 기반, 1024차원, MIT), `dragonkue/snowflake-arctic-embed-l-v2.0-ko`
(0.6B, 한국어 리더보드 82.14로 2위, 1위와 0.65점 차). sentence-transformers로 바로
로드된다. **API 비용 0 · 데이터 유출 0.** 1B 미만 모델에도 한국어 품질 절벽은 없다
(최상위 대비 4~7점 이내). — [KURE](https://github.com/nlpai-lab/KURE), [ko-embedding-leaderboard](https://github.com/OnAnd0n/ko-embedding-leaderboard/blob/main/README.md)

### 기각된 것들 (결론으로 오용 금지)

적대적 검증에서 **14개 주장이 죽었다.** 편한 결론을 지지하던 것들이 많다.

## 내부 실측 — 이 vault

### 규모

```
노트 4,014개 · 29.1MB · 약 9~12M 토큰 · 한국어+영어 혼용
평균 7.4KB/노트 · 예상 청크 1~2만
```

### 비용 (임베딩)

| | |
|---|---|
| 최초 전량 구축 | 약 $0.20 (API `3-small` 기준) · **로컬이면 $0** |
| 저장 | 25~75MB |
| 질의 | 1~2만 벡터는 numpy 브루트포스로 수 ms. **ANN·벡터DB 불필요** |

### 변경 빈도 — 자주 고치는 환경

최근 120일 git 실측.

```
.md 건드린 커밋 58개
  대량 마이그레이션(300+ 파일)  15회   ← 8일에 1번꼴
  일반 커밋                     43회   중앙값 30파일

주별 고유 변경   약 168파일 (vault의 4%)
120일 누적       2,195개 (55%)가 한 번 이상 수정됨
3회 이상 수정    145개 (7%)
```

**결정적 발견.** 대량 마이그레이션 하나(2026-08-18, 698파일)를 분해했다.

```
기계적 변경만 (태그 이동·frontmatter):  666  (95%)
의미 있는 본문 변경:                     32  ( 5%)
```

본문 첫 줄의 `#Log/Daily-Note`를 frontmatter로 옮긴 커밋이었다. **파일은 전부
바뀌었지만 의미 내용은 안 바뀌었다.**

이건 이 vault가 **이미 한 번 푼 문제**다. `monthly-elevate` v2.5:

> 내용 해시 방식도 검토했으나, 전역 sweep을 하면 전 문서 해시가 바뀌어 전부
> 「변경됨」으로 오탐된다.

임베딩 무효화에 같은 함정이 있다.

| 무효화 기준 | 그 커밋에서 재임베딩 | |
|---|---|---|
| 원본 파일 해시 | **698개** | 95%가 헛일 |
| **의미 텍스트 해시** | **32개** | 실제 바뀐 것만 |

의미 텍스트 = frontmatter 제거 + 인라인 태그줄 제거 + 공백 정규화.

돈은 어느 쪽이든 싸다. **진짜 이득은 "무엇이 실제로 바뀌었나"를 정확히 아는
것**이다 — sweep 때마다 전량 재계산을 기다리지 않고, monthly-elevate가 겪은
오탐을 반복하지 않는 것.

## 설계 권고

```
질의: "Redis 커넥션 풀 문제, 읽어볼 문서 골라줘"
   │
   ├─ 1. 메타데이터 사전 필터   type·tags·구역(200/300/400)   ← 이미 있음
   │
   ├─ 2. 벡터 검색             의미 유사 청크 top-k           ← 새로 추가
   │
   └─ 3. 그래프 확장(선택)     q near / q path 로 이웃 넓히기  ← 이미 있음
```

- **그래프의 역할을 고정한다** — 증거 저장소가 아니라 라우팅·이웃 확장. 원문이
  증거다. HippoRAG 2가 검증한 형태이고, 이미 그 모양이다.
- **저장은 SQLite + numpy로 시작한다.** 이 규모에 ANN은 불필요하다. 필요해지면
  sqlite-vec으로 올린다.
- **모델은 로컬로 시작한다.** 비용·프라이버시가 공짜이고 품질 절벽이 없다.
- **증분 갱신은 의미 텍스트 해시로.** 위 실측이 근거다.

### 구현 현황 — 2026-09-08 (`~/Desktop/Code/vault-vector`)

```
1. 메타데이터 사전 필터   됨   vv search --zone --type --tag   (인덱스의 doc 표, 같은 파서)
2. 벡터 검색             됨   4,201편 · 49,105청크 · 전수 내적 · 문서 = 최고 청크
3. 그래프 확장           됨   vv search --near — .vault-graph.db 의 near() 로 링크·역링크·태그공유
```

그 위에 셋이 더 붙었다. **증분 색인**(청크 텍스트 해시 — 이 문서의 「의미 텍스트 해시」 그대로,
1,073편 바뀐 날 12분·안 바뀐 날 1초) · **있음/없음/애매 판정**(골드 40 vs 볼트 밖 24 로 경계 둘,
없음·애매는 `absent.jsonl` 에 남아 써야 할 문서의 씨앗이 된다) · **배치 후보 `vv place`**(폴더의
문서 평균 벡터를 카드로, 정확한 폴더 top-5 83%; 데이터가 없는 폴더는 경로 텍스트 카드 72%).
수치와 결정은 `vault-vector/docs/architecture.md` · `placement.md`.

「아직 모르는 것」 중 **④ ANN 임계는 닫혔고**(전수 0.43초/4,050질의), **③ 청킹의 summary·태그
주입 효과**와 **① 교차언어**는 그대로 열려 있다. **⑤ 에이전트 도구 구성**은 vault-new 스킬이
답의 절반을 냈다 — place → 철학 → search(이웃) → new → 관계 관문 순서로 나눠 부른다.

## 아직 모르는 것 (정직하게)

연구가 **답을 못 준 것들**이다. 추측으로 메우지 않는다.

1. **한↔영 교차언어 검색** — 한국어 질의로 영어 노트를 찾는(또는 그 반대) 품질이
   어떤 출처로도 측정되지 않았다. 한국어 파인튜닝이 영어 검색을 얼마나 훼손하는지
   미측정. **혼용 vault인 내게는 이것이 모델 선택을 뒤집을 수 있는 변수다.**
2. **OpenAI 대 오픈소스의 실제 위치** — 신뢰할 head-to-head가 없다. 한국어
   리더보드는 오픈 모델만 평가한다. 답은 **내 vault에서 소규모 라벨링 A/B**뿐이다.
3. **마크다운 청킹** — 살아남은 근거 0건. 특히 이미 있는 80자 `summary`와 태그를
   청크 텍스트에 주입하는 것(Anthropic contextual retrieval의 저비용 대체물)이
   품질을 올리는지 미검증.
4. ~~**sqlite-vec/브루트포스의 한계와 ANN 전환 임계**~~ — **이 M4에서 직접 쟀다.**

   float32 1024차원 · 정규화 후 내적 · top-10 · 20회 최소값:

   | 청크 | 메모리 | 검색 |
   |---|---|---|
   | 10,000 | 39MB | 0.42ms |
   | **20,000** | **78MB** | **0.83ms** |
   | 200,000 | 781MB | 9.4ms |
   | 1,000,000 | 3.9GB | 42.7ms |

   **2만 청크가 0.83ms다. ANN도 서버도 필요 없다.** 램은 벡터(78MB)가 아니라
   임베딩 모델(fp16 약 1.1GB)이 먹고, 질의 지연도 검색(0.83ms)이 아니라 질의
   임베딩(10~50ms)이 지배한다 — **없는 병목을 풀지 않는다.** 저장은
   `vectors.npy` + 메타데이터 SQLite로 시작하고, 메타데이터 필터가 복잡해지면
   sqlite-vec으로 올린다. 개념 정리는 vault의
   `개인 규모 벡터 검색 — 서버도 ANN도 필요 없는 구간`.
5. **에이전트 도구 구성** — 단일 `search`로 합칠지 grep/graph/vector로 나눌지
   근거 0건. "agentic 루프가 그래프를 대체한다"는 주장은 기각(0-3)됐으므로 이
   설계 질문은 완전히 열려 있다.

### 근거의 한계

살아남은 벤치마크는 영어 위키 QA·영어 금융 표·영어 생의학이다. **"한/영 혼용 개인
노트에서 의미 유사 추천"을 직접 측정한 출처는 하나도 없다.** 한국어 임베딩 근거도
등급이 낮다(단일 관리자 리더보드, 오차막대·오염 통제·재현 하네스 없음).

특히 T2-RAGBench의 "BM25 > 밀집"은 저자 스스로 회사명·지표명 같은 정확 용어 일치
때문이라 밝혔고 정답이 전부 숫자다. **이 순위를 의미유사 추천에 옮기면 안 된다.**

## 다음 행동

1. **소규모 A/B로 모델을 고른다.** 내 vault에서 질의 20~30개에 정답 문서를 라벨링
   하고, 로컬 모델 2종(KURE-v1 · arctic-embed-ko)과 API 1종을 붙여 잰다. 위
   미지 1·2번을 내 데이터로 답하는 유일한 방법이다.
2. **가장 단순한 것부터 짓는다** — 헤딩 기반 청킹 + summary/태그 주입, SQLite
   저장, numpy 브루트포스, 의미 텍스트 해시 증분.
3. **BM25·리랭커·그래프 융합은 미룬다.** 벡터 단독이 실패하는 사례를 관측한 뒤에
   그 실패에 맞는 것만 붙인다.
