## 비목표

phase10 Step 4의 목록을 그대로 유지하고, 판정 결과로 두 줄을 더한다.

- 검색 품질 향상을 이유로 OWL 공리를 늘리지 않는다.
- VectorDB·임베딩·청킹을 구현하지 않는다.
- 전체 Vault를 자동 의미 추출하지 않는다.
- 저장 엔진을 먼저 교체하지 않는다.
- 에이전트에게 쓰기 권한을 주지 않는다.
- 트리플 수와 클래스 수를 성공 지표로 삼지 않는다.
- **어휘를 먼저 늘리지 않는다.** 순수 온톨로지 질문이 30개 중 3개다.
- **인용률이 낮은 대역을 채우려 하지 않는다.** 600·300의 낮은 인용률은 고장이 아니라 원자재의 성질이다.

## 계층 책임

phase10 Step 2의 표에 판정에서 나온 다섯 번째 갈래를 더한다.

| 계층 | 판정 기준 | 질문 수 |
|---|---|---:|
| **작성 계약** | **그 사실을 적는 방법 자체가 없다. Phase 12이 선행한다** | **18** |
| 기존 SQLite | 문서·태그·링크·경로만으로 정확히 답한다 | 3 |
| 온톨로지 | 개체 종류와 관계 의미가 있어야 답한다 | 3 |
| SHACL | 존재해야 할 값이나 허용할 구조를 검사한다 | 3 |
| 운영 규칙 | 상태 변경·재검토·우선순위의 절차적 판단 | 2 |
| Vector | 의미 유사 후보. **3부 구현 범위 밖** | 0 (2개가 부분 의존) |
| 기각 | 데이터가 없어 질문이 성립하지 않는다 | 1 |

### 작성 계약이 가장 큰 갈래라는 것의 뜻

계층 사이의 순서가 정해진다.

```
Phase 12 작성 계약  ─────→  나머지 전부
      │
      └ 이것이 없으면 온톨로지는 인스턴스가 0개인 빈 스키마다
```

phase12이 스스로 이렇게 적어뒀다.

> 입력 계약이 없으면 온톨로지는 어휘만 있고 인스턴스가 없는 빈 설계가 된다.

판정은 그 문장이 **예상이 아니라 현재 상태**임을 확인했다.

## 가장 중요한 발견 — 작성 계약만으로 어디까지 가는가

작성 계약이 18개로 가장 큰 갈래라는 것은 **온톨로지가 필요하다는 뜻이 아니다.**
그 반대일 수 있다.

### 실증 (2026-08-25)

`vault/graph.py:83`이 이렇게 되어 있다.

```python
for kind in ("builds_on", "supersedes"):
    for item in fm_list(fm, kind):
```

**엣지의 `kind`는 frontmatter 필드 이름에서 그대로 온다.** 그래서 필드를 늘리면
기존 SQLite 그래프가 그대로 받는다. 임시 vault를 만들어 확인했다.

```yaml
type: principle
evidence:
  - "[[사례 - 간헐적 500 에러]]"
contradicts:
  - "[[원칙 - 빠르게 닫고 넘어가라]]"
```

튜플에 `"evidence", "contradicts"` 두 개를 더한 것 외에 아무것도 바꾸지 않았다.

```
C04 · 이 원칙은 어떤 사건에 근거하는가
  → 사례 - 간헐적 500 에러.md

C06 · 서로 긴장하는 원칙
  원칙 - 추측으로 닫지 마라.md  ↔  원칙 - 빠르게 닫고 넘어가라.md

C05 · 근거 없는 원칙
  ✗ 원칙 - 빠르게 닫고 넘어가라.md
```

**RDF도 온톨로지도 추론기도 없이 답이 나온다.**

### 이 방식으로 답해지는 질문

문서 단위 관계로 충분한 것들이다. 18개 중 **12개**가 여기 들어간다.

```
C02 C04 C05 C06 C10 C19 C20 C21 C22 C23 C28 C29
```

frontmatter 필드를 늘리고 `graph.py` 한 줄을 고치면 끝난다. 2부의 결론이
그대로 반복된다 — **SQLite로 충분하다.**

### 이 방식으로 답해지지 않는 질문

여기서부터가 3부의 진짜 문제다.

| 필요한 것 | 질문 |
|---|---|
| **문서보다 작은 단위** | C07(가치) · C13(주장의 차이) · C17(결론) — 한 문서 안의 여러 주장을 따로 가리켜야 한다 |
| **시점과 변화** | C08(믿음의 변화) · C18(커리어 판단의 변화) — 같은 관계가 시간에 따라 달라진다 |
| **상태 분리** | 제안·승인·철회. frontmatter는 전부 asserted다 |
| **출처** | 누가 언제 왜 이 관계를 넣었나 |
| **관점 주체** | 주관적 진술. 「내가 그때 그렇게 봤다」 |

`500 Mind Compiler/Q7/_Patterns.md`가 근거를 `[[문서]] 4행`으로 가리키는 것이
증거다. **사용자는 이미 문서보다 작은 단위를 쓰고 있다.**

### 분기 규칙 — 파일럿 전에 적는다 (2026-08-26 결정)

파일럿에서 관계마다 **근거를 가리키는 데 실제로 필요했던 단위**를 기록한다.
문서 하나로 충분했는가, 섹션이 필요했는가, 블록·행까지 내려가야 했는가.

| 문서 단위로 충분한 관계의 비율 | 분기 |
|---|---|
| **80% 이상** | **규모를 줄인다.** frontmatter 관계 필드와 `vault q` 확장으로 간다. Phase 13·14는 축소판으로, Phase 12(작성 계약)은 유지한다 |
| **50 ~ 80%** | **혼합.** 문서 단위 관계는 frontmatter로, 나머지만 의미 그래프로 올린다. 두 층의 경계를 Phase 12에서 정한다 |
| **50% 미만** | **계획대로 간다.** 안정 ID와 의미 그래프가 정당화된다 |

이 수치는 파일럿 전에 정했으므로 결과를 보고 옮기지 않는다. 옮기려면 왜
옮기는지를 함께 적는다. 파일럿의 중단 기준(문서당 15분 · 재라벨링 60%)을 미리
적은 것과 같은 규율이다.

**분기가 「규모를 줄인다」로 나와도 3부가 실패한 것이 아니다.** 무엇을 만들지
않아도 되는지를 알아낸 것이고, 그것이 Phase 10을 먼저 한 이유다.

### 따라서 Phase 11의 세 번째 측정이 결정적이다

파일럿이 재는 것 중 「의미 단위가 문서인가 섹션인가 블록인가」가 **3부의 존폐를
가른다.**

```
문서 단위로 충분하다   →  frontmatter 필드 + graph.py 한 줄. 3부는 여기서 끝난다
문서보다 작아야 한다   →  3부가 정당화된다. 그때 온톨로지를 논한다
```

2부는 다 만든 뒤에 「SQLite로 이미 된다」를 발견했다. 이번에는 **만들기 전에**
그 갈림길을 알고 들어간다. 이것이 Phase 10을 먼저 한 이유다.

### SHACL 3개는 예외다

C16(저자 주장과 내 믿음 혼재)·C24(type 오분류)·C26(밴드 원칙과 실제 내용)은
**의미 그래프 없이도 지금 검사할 수 있다.** 기존 frontmatter와 경로만으로 된다.
Phase 16를 기다릴 이유가 없고, 기존 `vault lint` 확장으로 충분할 수도 있다.

이것이 3부에서 가장 빨리 값을 낼 수 있는 자리다.

## Vector 경계

3부는 VectorDB를 구현하지 않는다. 연결 계약만 정의한다. **구현은 옆 레포 `vault-vector` 가
맡았고, 2026-09-08 기준 아래 계약의 문서 단계까지 이어졌다** — 이 절 끝의 「구현 현황」.

```
chunk_id  →  artifact IRI  →  section/block  →  knowledge entity
```

### 규칙

- Vector 점수는 **검색 신호이며 asserted graph에 들어가지 않는다.**
- 의미 유사도만으로 `contradicts`·`informed_by`를 확정하지 않는다.
- 유사 후보는 답이 아니라 **별도 후보**로 표시한다.

### 부분 의존하는 질문 2개

| | |
|---|---|
| C06 긴장하는 원칙 | 관계가 적히면 온톨로지로 답한다. 안 적힌 것을 **찾아내는** 데는 Vector가 필요할 수 있다 |
| C11 가이드라인 모순 | 규칙이 자연어 문장이라 비교에 의미 유사도가 필요하다 |

둘 다 **먼저 작성 계약으로 시도하고**, 사람이 적은 것만으로 부족하다는 것이
측정된 뒤에 Vector를 검토한다. 순서를 뒤집지 않는다.

VectorDB 자체의 설계와 실측은 [`retrieval-architecture.md`](../notes/retrieval-architecture.md)에 있다.

### 구현 현황 (2026-09-08)

| 계약 | 상태 |
|---|---|
| `chunk → artifact IRI` | **됨.** `vault-vector` 의 `doc.path` 가 `node.path` 와 같은 키(볼트 상대경로, NFC). `doc_iri` 로 IRI 가 나온다 |
| `→ section/block` | 미구현. 청크에 heading 경로는 있으나 `section_iri` 와 잇지 않았다 — 감시 목록 |
| `→ knowledge entity` | 미구현 |
| 점수는 asserted graph 밖 | **지킨다.** `vv search --near` 는 그래프 이웃을 「문맥」으로 붙이고 점수를 섞지 않는다. `test_crossing_is_never_similarity` 유지 |
| 유사 후보는 별도 후보 | **지킨다.** vault-new 4부 관문 — 검색만이 근거인 관계는 되묻고, 위임받은 것만 `proposed` |

같은 파서·같은 경계를 쓴다 — `vault-vector` 가 `vault.scan`·`vault.frontmatter`·`vault.graph.in_graph` 를
직접 import 한다(경로 의존, Python 3.14). 복제본이 9일 만에 갈라진 뒤의 결정이다.

이쪽에서 저쪽으로 흘러간 규칙 하나: **「폴더가 type 을 말한다」**(문서 4,179 중 90.1%). 여기서는
`vault new` 의 라우팅 경고(`routing_warning`), 저기서는 `vv place --type` 이 그 type 이 없는 폴더를
후보에서 뺀다. 반대로 저쪽에서 온 사실 하나: 임베딩 이웃은 type 을 72.5%밖에 못 맞힌다(4,050편) —
type 은 벡터의 일이 아니라는 것을 규모 있게 확인했다.

## 성공과 실패의 정의

### 성공

- 승인된 역량 질문 중 **최소 하나**를, 근거 경로와 원문 위치까지 붙여 답한다.
- 그 답을 실제 결정이나 문서 수정에 썼다.
- annotation 유지 비용이 기존 Mind Compiler 리듬보다 크게 비싸지 않다.

### 실패 — 어느 것이든 하나면 중단한다

- Phase 11에서 문서당 15분을 넘고, 의미 단위를 조정해도 넘는다.
- 재라벨링 일치율이 60% 미만이다.
- gold set 50개를 만들었는데 답이 사람이 이미 아는 것뿐이다.
- 4주 뒤 아무도 그 질의를 다시 쓰지 않는다.

**읽기 전용 도구로 끝나는 것은 실패가 아니다** (D2). 아무도 안 쓰는 도구가 실패다.
